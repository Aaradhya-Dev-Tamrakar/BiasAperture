\chapter{System Architecture and Methodology}
\label{chap:methodology}

\Cref{chap:requirements} specified proposed system requirements. This chapter describes the proposed architecture, regulatory research crosswalk, project plan, and verification strategy. Design descriptions and planned checks are not evidence that every requirement has been implemented or validated.

\section{Design Principles}

The proposed architecture uses object-oriented design concepts and the \gls{solid} principles as guidance. Its five-module design separates ingestion, model access, metric computation, attribution, and reporting (\cref{sec:modules}); strategy and adapter patterns are proposed at the fairness and model interfaces (\cref{sec:patterns}). These design descriptions do not establish that interfaces are interchangeable or that all principles have been verified in the implementation. The shared schema and parallel work streams are part of the original project plan (\cref{sec:schedule}), not evidence of completed parallel development.

\subsection{Data Ingestion and Preprocessing Module}
This module is specified to load a selected benchmark or compatible custom dataset, validate image integrity, standardise image resolution and colour space via OpenCV, and align demographic annotation fields (race or ethnicity, perceived gender, age group) into the proposed internal schema (\cref{sec:schedule}). FairFace is the retained benchmark; UTKFace was excluded from completed scope.

\subsection{Model Interface Module}
The proposed model interface has two modes: direct in-process inference against a supplied PyTorch or TensorFlow model exposing a standard predict interface, and batch ingestion of a precomputed predictions file in \gls{csv} or \gls{json} format. Neither mode requires changing model weights; training and fine-tuning are out of scope.

\subsection{Fairness Metrics Computation Engine}
The proposed analytical core computes subgroup and intersectional performance and disparity metrics using AIF360 and Fairlearn. Comparing the backends can expose implementation differences, but does not constitute independent expert assessment. The implementation also has two distinct interval paths: the subgroup helper defaults to empirical percentile intervals with \(B=200\), and the adapters do not pass a higher budget; a separate global-summary path calls a configurable BCa bootstrap function. The subgroup default therefore falls short of proposed NFR-002's minimum \(B=1{,}000\). The proposal also specifies significance testing.

\subsection{Explainability Layer}
The reviewed logistic surrogate uses demographic indicator variables (race, gender, and age) to predict model outputs and summarizes associations. It does not operate on image pixels and cannot determine whether lighting, background, or another visual feature is a proxy or confounder. It does not establish causation or decompose the measured disparity. Image-based spatial \gls{shap} remains out of scope.

\subsection{Report Generation Module}
The proposed module assembles metrics, tests, and dataset and model provenance into a Model-Cards- and Datasheets-informed \gls{html} report. FR-006 specifies subgroup size, point estimate, confidence interval, and either a $p$-value or insufficient-sample flag. The current subgroup interval default is \(B=200\) percentile resamples, not the NFR-002 target of at least 1{,}000. The proposed Article~10, Annex~IV, and NIST references are research traceability and do not certify compliance.

\subsection{Orchestration and Configuration Layer}
A lightweight layer coordinates the pipeline end to end, dataset selection, model connection, metric selection, and report generation, behind a single entry point, and exposes a command-line interface with declarative execution flags through which an auditor specifies the audit parameters (FR-008). The dataset's licensing terms must be displayed and explicitly acknowledged before an audit is executed (FR-009).

The proposed workflow begins with the auditor specifying the dataset, model or predictions file, and metrics. Its two model-access modes are direct in-process inference and ingestion of a precomputed file. The planned case study uses FairFace; UTKFace was excluded from completed scope.

The workflow specifies computation of the Core Four metrics, sample-size checks, statistical tests, and demographic-surrogate associations. The output is a research report, not a compliance report. Subgroup confidence intervals currently use the percentile bootstrap with default \(B=200\), which is below the proposed NFR-002 budget; these intervals are not BCa intervals and are not based on at least 1{,}000 resamples.

The proposed design can be discussed in relation to the NIST AI RMF's Govern, Map, Measure, and Manage functions; this alignment does not mean the framework's outcomes have been satisfied. The demographic schema relates to Map, and metric calculations relate to Measure. Measure 1.3 calls for regular assessment by internal experts not involved in development or by independent assessors. A comparison between Fairlearn and AIF360 is not independent assessment and does not meet that practice. Manage, including prioritization and response to identified risks, remains outside the diagnostic scope.

\section{Project Plan and Schedule}
\label{sec:schedule}

The work packages in \cref{tab:wbs} record the original proposed eight-week schedule. They describe planned sequencing and ownership, not reported completion status.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{src/images/gantt.png}
    \caption{BiasAperture project schedule, work packages WP1--WP5.}
    \label{fig:gantt}
\end{figure}

WP1, \emph{Classifier Selection and Schema Lock}, was planned to select the classifier baseline and define the demographic schema: \texttt{image\_id}, race, gender, and age fields, true and predicted labels, and metric output fields. Its planned completion was Milestone~M1, \emph{schema locked}.

Under the plan, WP2 (Stream~A, test-matrix construction) and WP3 (Stream~B, report scaffolding) would proceed in parallel: Stream~A would curate the FairFace-based dataset and predictions, while Stream~B would build an \gls{html} report template against a mock metrics dictionary. Their planned convergence was Milestone~M2.

WP4, the \emph{Statistical Detection Engine}, was planned to consume the schema-aligned test matrix and produce the metrics dictionary for the report template. Milestone~M3 was defined as its planned end-to-end validation point.

WP5, \emph{Integration and Mock-to-Real Swap}, was planned to connect engine output to the report template and complete with a case-study run and report bundle at Milestone~M4.

\section{Verification and Validation Strategy}

The verification strategy proposed for the project is to compare statistical routines with known reference values, validate data against the specified schema, and assess runtime and report completeness against the requirements. These are planned checks, not reported results in this chapter. In particular, no measured runtime or completed end-to-end case-study result is asserted here. NFR-002 remains unmet for subgroup intervals in the reviewed implementation because their percentile-bootstrap default is \(B=200\).
